## Context

现有 Work/Attempt/Slot/Grant/Outbox 已由 T2 事务写入，但手工构造的输入可缺业务事实，确认 API 尚未接入，缺按项目轮询的准入服务。准备角色与实施角色共享两个 Run 槽位。

## Goals / Non-Goals

**Goals:** 版本化 DAG 校验和读取；当前成员依据下明确确认；有界、可恢复且持久公平的准入；按原 operation 查询已发送结果。

**Non-Goals:** 用 A2A completed 代替验证；由调度器修改计划；假装实际 Runner 可用；在本变更落地 P1-05/P1-06 的 Git 和验证执行器。

## Decisions

1. 计划结构验证复用纯函数，来源、预算、能力和当前指针由 Worker 在短事务重验。DAG 使用稳定 ID、显式依赖输出槽及完成条件；相交写范围必须存在拓扑先后。
2. GET 返回不可变图与 reviewHash，当前草稿具备 ETag。确认以当前成员权限→原键→CAS→版本／hash→图和必要题顺序校验。同一决定不可重复；历史仅可读。
3. 调度轮询已确认的 Run，按上次服务序号公平选择项目，按拓扑层级和稳定顺序选工作。依赖成功必须是同 WorkRevision 的已核实业务状态；completed-with-findings 需要独立验证事实，普通失败不满足。
4. 事务内复核剩余容量、预算、Runner 资源、冻结输入、当前代际与角色配置，保存 Attempt、槽、许可、Outbox、事件及轮询游标。显式配置缺失则不自动准入。不得凭空构造 Runner 资源或可运行工具。
5. 派发原请求持久记录 SENT；使用锁定 SDK 走绑定 Card 和 JSON-RPC。遇到未知结果先查原操作受理事实；仍未知则保留槽位和诊断，不能重新创建 Attempt。A2A Task 完成后仍由后续服务验证和集成。

## Risks / Trade-offs

- SQLite 单 Worker 需保持短事务；按页选择候选，网络和文件操作在事务外。
- 老计划仍可查询；不满足新校验的计划需修订并重新确认。历史状态不回填成通过。
- 缺真实资源时，仅使用显式本地测试夹具证明控制规则。
