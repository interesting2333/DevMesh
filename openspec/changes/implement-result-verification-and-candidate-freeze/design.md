## Context

See proposal.md。当前 `testerOutput` 只约束报告引用的 targetCommit 相等；Runner 输出有准确 job／operation／request hash、路径、SHA-256、大小和退出事实，PipelineCoordinator 仅采集原作业事实；issues 工具也明确 finding 不等于验证通过。`recordVerifiedWork` 是可信 IPC，现由调用方直接提供 success/findings，尚无原报告采集、独立解析或 ReleaseCandidate 冻结。模板固定 Vitest 4.1.11／V8，输出 Istanbul 兼容 coverage-final.json，已有完整业务 include，适合实现明确版本的有界解析器。

## Goals / Non-Goals

**Goals:** 按 D2 ResultVerifier、D4 §3/6、D5 事务与引用规则，将原执行／原报告、源码范围、独立质量计算、Work 验证和候选修订闭合；确定失败与未知分别保留。覆盖 T10、R07/R12/R13/R19。

**Non-Goals:** 降低 80/70 门槛；在控制面执行生成业务或报告内脚本；把脚本化作业视为真实 runsc；在本包实现接受后的数据迁移／路由切换，或把人工检查自动判为通过。

## Decisions

### Trusted policy and immutable report inputs

新增版本化质量策略契约，冻结 requiredCheckIds、检查种类／生产侧、批准命令、测试身份与需求映射、业务 include/exclude、必要报告集合和零分支 N/A 规则；规范哈希与准入 inputManifest.checkConfigHash 一致。它是可信模板／项目配置，模型工具不能注册或放宽。现有仅含配置哈希的历史激活不倒填“已验证策略”，继续保留待配置，不推定通过。

可信采集服务以原 pipeline/job 查询实际状态，流式读取有界 Runner 输出和日志并核实 SHA／大小。先持久验证原操作与固定输入，报告内容用专用内容 target 在登记事务内建业务外键。原字节落盘后独立解析，不从 Agent 提供的 status、百分比或 artifact 名称推导通过。请求丢回复只查原操作；SENT/未知作业不重跑。前后端报告由策略指定的生产侧与来源作业匹配，不能用重复上传同一报告充数。

Runner 已持久保存每个原 Job 的批准 argv；公开事实新增由这份不可变 execution_json 推导的 commandHash 与实际 runnerId，不发送宿主工作区路径，也不从重启后的当前配置重算。PipelineCoordinator 同时保留结束时间与该原执行身份。旧 pipeline 终态字节没有这些字段时只作幂等查询比较，不把新的观察字段回填到旧记录或默认视为新的质量证明；新质量验证缺准确执行事实时保持缺失。

### Pure bounded report and coverage evaluation

独立 TypeScript 包不依赖模型执行，先实现纯解析和计算，再接可信采集与 Worker。首版原格式为模板实际使用的 Istanbul/V8 JSON 及明确版本的结构化测试结果，命令／类型／构建报告仍绑定原 Runner 事实。未知格式明确失败，不自动猜测。

准确 Git manifest 冻结全部业务文件及内容哈希；可信插桩／报告映射保留每个文件的完整位置集合，包含未执行文件。相同 SHA 的 overlapping producer 对共享源码必须给出一致位置身份；冲突、无法 source-map、缺文件或缺必要 producer 返回缺失／过期，不把未知位置当已覆盖。路径只接受规范相对源码名，绝对路径仅由部署固定 prefix 映射；拒绝越界、重复规范路径和大小写歧义，不读取报告指定的宿主路径。计数、文件量、深度与正文有明确上限。

完整位置拓扑是可信执行前输入，独立于待验证命中报告并固定 sourceManifestSha256／topologySha256；只读的批准工具链或可信预处理负责生成，模型和普通工具不能自行登记。不能从同一份命中报告推导分母后将它当作独立证明。首版解析实际模板中行尾 null 为准确源码行尾，隐式 if/else 无位置保留 null 备选身份；其他不可映射位置拒绝。已确定失败的原执行可保留原报告数量供解释，整体仍为失败；未知作业仍待核实，同一 Job 不计为两个生产侧。

采集分为执行前 `prepare` 和执行后 `collect`。prepare 只接受部署注入的可信映射 provider，缺配置拒绝，核对其全量 Git 文件／内容哈希及工具链身份，并在专用 SOURCE 内容 ACK 后允许托管 verification 工作区发送流水线。SOURCE 声明／登记与 stage 首次 SENT 在 SQLite 中互斥，不依赖控制面与远端时钟一致。追加迁移 22 固定 producer 到原 pipeline／ordinal／stage operation 的绑定，首次发送前建立、之后不可换作业。collect 仅 GET 原作业／原输出索引，流式校验大小／SHA；不调用 start／renew／stop，也不执行报告中的脚本。首次缺失报告或未知查询保持 PREPARED 和明确待核实代码；原字节已登记后可从本地内容恢复，终态回执丢失只返回原结果。映射 provider 的生产工具链和 Runtime 自动组合仍须单独接入与验证，独立映射夹具不能替代它。

Istanbul statement start.line 去重形成可覆盖行，同一行任一 statement 有命中即覆盖；分支身份取类型、原位置和备选路径位置，不使用各生产侧自增数字 ID。共享源码命中按身份并集，次数不重复累加分母。阈值使用整数交叉相乘，不因浮点或显示四舍五入放行。非空业务范围和有效完整映射下零分支需冻结规则及证据；空业务集合不能 N/A。

### Verification transactions and compatibility

向前迁移保存验证操作、冻结 basis、原报告元数据／字节引用、逐项 PASS/FAIL/MISSING/NOT_APPLICABLE/STALE 和最终解析结果。Worker 从原源码 ACK／验证分配、Runtime 角色候选、当前 Work revision／epoch、策略与报告来源重建输入，异步读字节／解析在事务外；提交前再次核对 basis。未知写工具／Runner Job 阻止完成验证与冻结。

ResultVerifier 只通过可信接口提交可复核计算；普通 MCP 仍只记录发现和原 Job。将调度 `recordVerifiedWork` 的正式验证入口绑定这些持久事实，保留必要历史夹具的显式兼容路径，但生产托管来源不能经旧接口绕过。更改行为需同步增量规格和实际测试，不把伪造 success 留作部署默认。

正式 Work 完成保存独立的不可变评估和内容回执：原 Runtime 候选及其规范字节哈希、当前计划／需求／Work／epoch、源归档或原质量操作、逐项完成条件、准确输出与最终证据共同固定。读候选正文及复核内容可用性在事务外，登记与应用时 Worker 重新计算并核对依据。Tester 的状态以原质量事实为准；模型报告字段仅为候选，不是通过凭证。无原候选、无准确源码／配置、未知副作用或必要人工项待定时不完成。无法证明固定源码的命令检查显示 MISSING，不能用可变开发目录上的旧执行放行。

新 `recordVerifiedWork` 必须引用已 ACK 的 Work 评估，调用方提供的 outcome／evidence／outputs 必须等于评估派生值；`transitionAttempt SUCCEEDED` 不再接受一般证据直接结束任务。既有已提交操作仍按原键查询／重放，既有终态和 verified_work_results 保留；历史测试夹具在测试代码中显式种入旧事实，不在应用提供 fixture 开关或生产绕过。新证据正文与 artifact 外键在同一内容登记事务落定，之后保持不可变。

### Findings, forward repairs and candidate revisions

复用已有 issue 历史，不覆盖原失败；缺陷保存复现、预期和报告引用。新的受信任修复规划操作以原失败为依据，生成 developer fix → tester reverify 的前向 Work，最多两轮，纳入 DAG 30 项与当前计划确认约束。涉及需求／接口变更进入已有审查，不自动确认。复验只能关闭确切修复 SHA 和原缺陷，旧通过不沿用。

独立失败与模型声明分别保留：只有原质量验证中能定位的失败检查／测试及准确原报告能作为受信任自动修复依据；无法映射、缺失工具链或仅模型声明的问题保持待核实。复现信息固定原批准命令、测试身份、代码／配置和输入；预期来自冻结必要检查与需求验收。以原 Work 验证和失败身份去重，恢复原回执不能重复创建缺陷或覆盖失败历史。

确定的原失败随正式 Work 完成在同一事务导入现有 issue 与不可变 revision；新增来源表固定 Work 验证、质量操作和 checkId，关联冻结命令／镜像／原 Job、原需求验收正文和材料哈希。只有原执行已正常结束、时间有序、无基础设施错误或停止请求的可复现失败进入该入口；原质量 FAIL 与未知／待核实仍分别保留。新的只读查询允许当前项目成员查看历史，完成／暂停后不依赖已撤销的 Agent Grant。修复关联和复验关闭使用受信任负责人命令及原操作回执；MCP 继续支持普通 finding 的原流程，不能改写独立失败的来源或绕过受信任关闭。

关闭以新 Developer 与 Tester 的 APPLIED Work 证明、准确已 ACK 合并来源和原质量操作为准，并核对冻结检查、需求与配置。只有全部独立检查与新 Work 通过才记录 PASSED／关闭；原检查再次独立失败记录 FAILED 并保留两次失败；新模型声明或缺失条件记录 NOT_VERIFIED，不制造新的独立失败结论。三种结果都追加历史，不修改原报告与失败。

追加修复计划时，为确实未改变的已完成 Work 保存显式沿用记录，关联原计划、Work revision／epoch、输入／结果和原审查依据，由新计划确认覆盖这项沿用决定。调度依赖与源码组合必须查询该记录；不能把所有旧结果因为计划版本变化而丢弃，也不能将旧 Tester 通过直接当作新代码通过。需求、接口、策略或 Work 内容变化应重新审查与验证。原失败可作为 findings 前驱，修复和复验使用新节点，计划未确认不得派发。

前向修复使用 PREPARED → READY → PUBLISHED 的私有日志和稳定 writeKey／publishKey。计划字节先在专用内容 target ACK；发布事务重核原计划、需求、未解决独立缺陷和所有已完成原结果，原子追加新计划及沿用记录，不变更需求修订、不自动确认。每个 Run 最多发布两轮，每轮两项新 Work；超过 30 项、存在活动／未知副作用、写入范围扩大或涉及需求／接口变化时拒绝自动规划。当前有界实现将计划与沿用结果的序列化视图限制在 192 KiB，超限需显式处理，不截断原事实。

沿用记录固定原计划确认、Work 定义／epoch、原输入／角色／模板／配置哈希、原结果／证据／正式证明身份；历史兼容结果保留 HISTORICAL 来源。调度与源码组合共享同一解析器，只有新计划确认后才使用沿用结果；源码组合按记录核对原决定，而新 Work 使用新计划决定。新计划 review 显示沿用摘要和 carryForwardHash，确认必须同时提交它；老确认请求不补默认值，以保持原请求哈希和回执重放。实际确认与原缺陷关联在同一事务落定，计划发布本身不派发修复。新修复及复验准入必须保持原冻结模板与质量配置，新的代码仍需新的准确 SHA 质量验证。

源码组合会生成准确的合并提交，复验目标可能不同于单个 Developer 的 resultCommit。缺陷关闭需同时证明：原修复 Work／归档准确、受信任合并候选确实包含该修复来源、原质量操作测试的就是该合并候选 SHA，以及新 Tester 的正式评估通过。不能仅凭调用方 SHA 或单个分支提交相等推断已复验，也不能用较早通过的候选关闭后续修复。

候选冻结采用原操作与不可变 candidateRevision：从当前 run-candidate 源码 ACK 和已验证集合推导准确版本，核对必要检查、缺陷、未知写操作、构建哈希／镜像、数据方案及必要材料。自动检查通过才产生可供人工审查的候选，人工项显示待完成；P1-07 在接受事务再次复核全部人工及数据准备凭证。候选冻结不移动接受指针。材料变化生成新修订，旧审查不迁移。

源码组合中的合并提交包含操作身份，因此相同来源在新的组合操作中重新合并也可能得到不同 SHA。最终 run-candidate 必须保留已测试的准确工作输入提交：可在来源归档、计划和需求完全等价时，通过受信任 Git 适配器核实原 ACK／refs 和 manifest，再以独立原操作发布同一提交；禁止仅比较 tree 或为新 SHA 复用旧报告。原合并步骤／ACK 保持原身份，不伪造为新操作的步骤。

人工检查待处理时，允许创建“自动检查通过、人工待完成”的可审查候选，但不把原 Work 的 READY／PENDING 记为完成。该路径仅接受非人工检查全部 PASS、原质量 automaticStatus=PASS、无候选缺陷／缺项或未知副作用的原评估；人工条目逐项显示 PENDING。后续接受必须绑定该候选的人工事实并重新核验，原自动报告和待审评估不回写为通过。

交付镜像内容身份与构建来源分别核实。内容校验采用有界 OCI 1.1.0 格式，读取实际 manifest／config／layer 原字节，计算 manifest digest 及有序未压缩 diff_ids；固定源码及构建产物标签只是交叉校验，不能取代原构建 Job。仅接受 Linux amd64／arm64 与 tar／gzip layer，拒绝未支持格式、重复 JSON 键、缺失或额外 blob、哈希不符及超限解压；不拉取标签或执行镜像。Worker 还须固定批准构建 producer／原命令、准确分配的工作区、原 pipeline／Job／输出哈希及内容 ACK；缺少真实生成镜像时保持材料缺失。镜像可运行与健康检查在后续预览／接受流程验证，内容身份通过不等于它们通过。

实际构建文件哈希、生成应用预览镜像 digest 和数据方案必须有各自准确源码与原生产侧来源。聚合质量 resultRef 不能当作构建文件，测试执行基镜像 digest 也不能当作生成应用镜像；缺受信任生产侧事实时保持缺失并拒绝冻结。未配置 Docker／Linux Provider 的离线开发可测试拒绝与明确的受控适配器事实，不宣称生产构建通过。

交付清单在 Tester 准入前固定到质量策略 `delivery`，随 checkConfigHash 绑定原输入；包含批准命令 producer、架构及准确材料键／输出路径。交付策略只能登记与之完全一致的版本，不能在报告通过后删减清单。迁移 27 保存原质量依据、原 Job、原输出索引／SHA／大小及材料稳定写入键；采集器仅查询原 Job 和按索引读取，原内容 ACK 后校验实际 OCI 字节及规范 JSON 数据方案，最后重核当前依据。丢回复恢复原操作和内容，不触发新构建。首次初始化只用于无接受版本的项目；保留迁移需准确同 Run artifact，替换需绑定原数据方案哈希的负责人决定，采集阶段不执行数据动作。运行说明／协作记录／角色配置当前固定字节与来源，其语义和导出脱敏仍是后续检查，不能凭内容存在就声称生产可用。

迁移 28 在既有 release_candidates 外保存原冻结操作、不可变正式 Work 证明与内容外键，不将既有无来源候选升级为新证明。冻结使用标准 meta／If-Match，在当前准确 run-candidate 来源和托管 head 一致时核对最终 Tester 的原质量及交付；历史沿用必须有确认快照和原 APPLIED 正式证明，HISTORICAL 不能放行。前向修复保留的旧失败不作当前通过依据，新的最终 Tester 必须在当前计划以准确源码／配置取得原验证。唯一未结束 Attempt 可为非人工项全通过且 Runtime 已结束的最终 Tester 人工待审；其他活动 Attempt、未知工具／Runner／Git／准备操作及未解决高严重问题拒绝。

新增候选正文限制 192 KiB，与预检哈希集合序列化合计限制 240 KiB，为 Worker RPC 留出元数据空间；超限拒绝而不截断证明。标准操作回执、候选修订／材料引用、REVIEW 状态、资源版本和 CandidateUpdated 事件在同一事务提交，失败全部回滚。原键重放返回同一候选，不重新采集或执行；新操作建立新 candidateRevision，逐项保留人工待审而不继承决定。详情保留完整冻结依据，列表只返回有界摘要，当前查询取最新修订。新修订建立后旧修订的当前资格失效；源码、计划、配置、材料及副作用变化同样使资格 STALE，原正文不回写。这一步不产生 Release，不推进接受指针，也不替代 P1-07 的接受前复核。

冻结前由显式 `CandidateFreezer` 取得不可变依据，实际读取正式评估、原角色候选及其 artifact 引用、质量材料和原交付文件，按哈希核对正文与可用性。按内容哈希去重，最多 2048 项／512 MiB、单项 64 MiB；不加载或执行材料中的代码。最终命令携带准确 basisHash 与已读内容集合，事务再次核对依据、内容 READY／所属 Run 并固定其业务外键。实际缺失或损坏由内容库记录，不把未发现的文件缺失伪装成成功预检；预检期间来源改变也不能提交。原冻结成功后恢复只用原操作的已固定依据和内容集合，不重做预检，也不因当前已过期而新建候选。

## Risks / Trade-offs

- 不可信报告／超大数据 → 固定格式、上限、来源作业、字节哈希、位置和完整范围校验，不执行脚本。
- 自报覆盖率刷分 → 全量业务清单、必要 producer、原始位置计数，缺失不视为 0 分母。
- 历史可信 IPC 绕过 → 正式托管完成必须匹配持久验证；兼容范围显式测试，不宣称历史材料具有新证明。
- 解析后来源改变／GC 竞争 → basis 重核与内容 target 原子外键；旧报告保留，候选新修订。
- 无 Linux、模型、真实 Runner 资源 → 本地格式／存储／协议组合照常实施；真实执行来源和门槛逐项记未执行，不伪造通过。
