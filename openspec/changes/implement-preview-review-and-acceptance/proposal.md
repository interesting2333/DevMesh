## Why

父工作包 P1-07（预览与人工接受）。现有代码能冻结准确源码、原验证及交付材料的不可变候选，但没有逐项人工审查、独立预览／dataset、T5 接受或发布恢复；候选 READY 不能等同用户接受。按用户已授权的连续实施，先完成不依赖真实模型、OIDC、Docker／gVisor 的服务和协议验证，正式工作包仍等待 P1-06／G0。

## What Changes

- 建立候选版本绑定的逐项审查、人工结论和只读投影，保留操作者、操作、预期、观察、证据与历史；下载／打开预览不触发接受。
- 增加 dataset、预览、接受准备与发布任务的向前迁移和持久操作；外部动作位于事务外，未知动作核实原对象。
- 实现独立 origin 的预览访问边界、短期用途凭据、到期／停止与业务数据保留。
- 增加独立 RELEASE 用途的已发布应用入口；固定当前接受指针、路由代际与原服务身份，使用独立票据／会话和 Runner 本地转发。其未确定写入与预览写入共同阻塞接受、发布和旧门恢复。
- 实现两阶段接受：固定审查与数据依据，外部数据／镜像准备，T5 原子保存 Release、接受指针、Run 完成与 promotion Outbox；提交后发布失败独立恢复。
- 通过可信宿主工厂显式装配接受准备消费，核实原策略／主体／Runner绑定，有界扫描未决原工作、独立更新健康并在停机时排空已开始调用；默认未配置关闭，不自动T5或发布。
- 通过独立可信发布工厂恢复已接受版本的原Outbox，有限扫描当前未决Release，沿用原Runner阶段许可续接；停止新接受不撤销显式原发布恢复权限。
- 通过独立可信撤销工厂消费已持久确认的原决定，串联Runner清理和原完成核实；停机停止新阶段授权并排空数据Worker之外仍在执行的authority调用。
- 记录 D01～D08 的适用本地验证与缺项，持续迭代中旧数据写门／最新快照的完整业务验收仍由 P3-01 复核。

## Capabilities

### New Capabilities

- `preview-review-acceptance`: 准确候选的逐项人工审查、隔离预览及 dataset、数据准备、原子接受和发布恢复。

### Modified Capabilities

无。现有未归档的候选冻结与托管工作区变更作为实施依赖，不把它们伪装为已完成的主规格。

## Impact

验收准备数据适配器的 Worker 超时／退出须保留父进程中未结束的授权、物理 custody 与可信迁移读取调用，真实排空后才结束原调用并释放名额；与既有消费者停机排空保持一致，原不完整日志只查询、不重做初始化或获取围栏。

涉及 storage-sqlite Worker／迁移、contracts、result-verifier 的候选复查、Runner 与预览网关适配、平台 API 和针对性协议／事务测试。沿用 Node 24、TypeScript、SQLite 单写与官方 A2A／MCP 技术栈，不增加普通模型写权限或默认公网发布。依据 design/03 用户流程、design/04 §6～8、design/05 T5、实施文档 P1-07 与产品场景 D01～D08；基线规则不变。真实身份提供者、生成应用构建运行／健康、Linux/runsc 和真实数据迁移缺项单独保留。
