# 审查变化后的替换再次确认

父工作包P1-07，关联4.1／5.1。准确候选REPLACE数据方案固定decisionId，而reviewHash随追加人工结论变化。原acceptance_data_decisions以decisionId为唯一键，第一次确认后无法对新的reviewHash再次确认；不能通过更新或删除原决定解决。

## 决定

新增前向迁移45与不可变acceptance_data_confirmations历史。原acceptance_data_decisions保留第一条确认作为固定锚点，迁移将每条已存在确认原样复制到新历史，不改变其操作、依据、操作者或时间，不生成新批准。新历史以operationId唯一，decisionId／reviewHash／actorId唯一，并通过数据库约束核实其候选、manifest、来源和数据方案与锚点相同；只追加准确reviewHash与当前actorId对应的新确认，禁止原记录更新／删除。

既有独立确认命令、公开契约和页面保留。第一次确认在同一原操作事务写入锚点和历史；再次确认在当前owner、准确candidate revision／manifest／review／source／data plan／decisionId及Run If-Match通过后仅追加历史。候选接受投影和准备准入按完整当前依据读取历史，旧确认永远不能授权新审查。当前Run条件通过且当前操作者已确认当前依据时，不同新键返回明确409；原UUID恢复同一旧结果并仍检查当前权限，不刷新确认或改变当前资格。并发新确认只准入一个，任何写入或事件失败完整回滚。

不新增模型权限、物理后端或接口。后继再次确认后需实际运行原数据准备、只读健康及第二轮T5；另验证44→45迁移保留旧行、DDL／历史失败回滚、跨锚点拒绝和追加不可变。真实身份、Linux围栏、第二轮发布与完整产品流程仍分别验收。

再次确认的并发条件：成功确认推进Run版本；并发持相同旧If-Match的另一请求返回412，最新If-Match下重复当前已确认审查的新键返回409。保持原键恢复与当前权限核实，不调整版本前置校验顺序。

原冻结依据仍有效且多个owner并存时，首次决定不锁定其他当前owner的后续明确确认。确认历史逐行保留actorId，并以decisionId／reviewHash／actorId去重；新owner不能借用其他人的确认，须在当前权限与Run条件下追加自己的明确确认。原actor不变，已撤权者原键重放仍拒绝。数据库固定锚点约束不要求后续actor与第一位actor相同，当前身份授权由同事务领域命令核实。

原冻结／上游操作依赖的主体权限失效时，候选继续陈旧，其他owner的确认不能恢复它；需要先产生有效候选。本次验证多个当前owner对仍有效候选分别确认，并验证原冻结主体失去owner权限（包括仅保留operator）时不放宽既有资格检查，不宣称完整owner交接产品流程。
