## Recorded preview dataset consumption

Parent P1-07 / tasks 2.2, 2.3 and 5.1. `startPlatform` accepts an explicit trusted executable `previewDatasets(services)` factory. It requires durable storage, independently of Input API, identity, preview access and model configuration. No JSON / public HTTP / MCP backend registration or default physical provider is introduced. All later host composition must succeed before the consumer starts. This consumer only advances existing owner-recorded dataset operations; it never chooses a data plan, creates another dataset, starts a preview, accepts or publishes.

Each immutable binding contains original projectId, policyHash, backendPrincipalId, backendRef, runnerId and DatasetPreparationBackend. Startup verifies these against the committed original policy through getPreviewLifecycleScope. Public adapter methods are pinned without mutating the caller and configured remains dynamic. Each backend invocation verifies the original effect kind / project / policy / request backend / Runner. The adapter remains responsible for its internal implementation and bounded I/O.

The private listPreviewDatasetWork reads only DATASET_PREPARE in PREPARED / SENT / UNKNOWN. Terminal data history and all preview effects are retained outside this work page. Each pass visits a rotating bounded set of projects with at most one page per project. Limits match preview lifecycle consumption: 1–32 projects / scopes, 1–2 concurrent projects, 1–20 items per page, 1–10 second polling. Per-project work is serial; tick coalesces; end-of-page wraps to zero; one scope's failure does not stop other scopes. Safe codes are retained instead of arbitrary backend error text.

PREPARED can obtain the existing single dispatch grant; SENT / UNKNOWN only inspect the original. DatasetPreparer checks admission after preflight and supplies final authorization that rechecks the original control writer's verifyPreviewExecution, current owner / candidate / source and closed state. stopAdmission closes all preparers immediately; stop drains actual pass / loop before storage disposal. No fabricated cancellation or automatic failure of uncertain originals is used.

LocalSqliteDatasetBackend requests authorization from its dedicated file Worker immediately before creating an original directory / journal. Read-only preflight and original-journal inspection remain unchanged. A direct trusted caller may omit the optional callback for compatibility; this is not a public authorization mechanism. DatasetPreparer / the host consumer always supply their authorization. A declined or unavailable authority returns UNKNOWN and leaves no new original journal. Worker timeout closes authorization and terminates the file thread, but the parent call and concurrency slot remain occupied until any already-started authority RPC actually returns. A late success cannot authorize an exited Worker. No data / Runner journal schema, old SQL migration or dependency changes are needed.

Validation uses actual control and file Workers, real application SQLite bytes, original journal / receipt, host stop / reopen, real timeout and explicit dispatch / physical-result ACK loss. Source candidate / Git / OCI facts and controlled container facts remain fixtures; this increment does not prove physical Linux isolation, production migration, enterprise identity or a complete successor preserve / replace acceptance.
