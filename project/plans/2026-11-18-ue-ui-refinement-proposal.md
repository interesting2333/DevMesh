# DevMesh 桌面端 UE / UI 优化提案

状态：用户已确认实施；按本提案完成桌面端两阶段优化。

范围：按用户最新要求，本轮聚焦桌面网页，移动端优化暂缓，不纳入本轮实施和验收。

依据：当前本地工作台的1600×1000页面实测，以及上一轮真实模型对话截图。沿用用户确认的深色、左侧导航、上方对话／下方输入、按需执行详情方向。

## 1. 设计目标

用户进入后能明确知道“从哪里开始、助手正在处理什么、什么时候需要我决定、怎样查看成果”。视觉重心放在需求表达与助手回复上。完整计划、工作记录及配置通过按需详情承接。

保留连续对话的结构，统一空间、字体、控件和状态反馈。当前稿中的任务和操作均为设计示意，不代表真实执行结果。

## 2. 当前观察与建议

| 当前表现 | 体验影响 | 建议 |
| --- | --- | --- |
| 1600px宽屏侧栏宽288px，主区内容上限1024px | 短回复显散，长回复阅读跨度大 | 侧栏240px，可收至64px；正文760～840px居中，与输入框共用对齐线 |
| 桌面输入区高202px | 空输入占据较多可阅读空间 | 空输入112～144px，输入后按内容增长 |
| 对话正文14px，输入文字反而更大 | 助手回复阅读负担较高 | 正文16px，行高约1.7～1.8 |
| 用户消息采用左竖线，作者标签与正文区分较弱 | 用户输入、助手回复、任务进展容易连成同一层级 | 用户轻底色气泡，助手开放正文，进展采用轻量单行摘要 |
| 首次输入直接成为完整任务标题 | “你好”或长句进入导航，难以找回 | 明确任务后提取简短标题；支持手动改名，长标题完整内容可查看 |
| 无任务时打开执行详情主要是空说明 | 面板价值较低 | 首页默认隐藏执行详情；已有任务时展示目标、当前阶段、资料和能力 |
| 确认按钮目前先把一句话填回输入框 | 用户容易认为已确认，实际还需再发送 | 改为直接提交绑定当前方案版本的确认动作，并明确显示结果 |

## 3. 首页

欢迎标题保留一个，副文案用一句话说明可输入、可附文件、可先讨论。三个示例缩成轻量按钮／紧凑卡片，示例选中只填草稿并允许编辑。

欢迎区、示例和输入框使用相同内容宽度。保留有组织的留白，控制引导和输入之间的距离。进入真实对话后收起欢迎内容，让首条输入自然接续。

底部不恢复已删除的常驻上传限制、草稿保存成功和项目名称表单；格式限制放在附件入口说明中，保存异常与恢复操作仍需明确可见。

## 4. 对话与任务状态

- 用户输入：轻量深灰气泡或清晰缩进，正文与助手使用相同可读字号；附件以真实文件名标签显示。
- 助手回答：开放排版，统一标题、段落、列表、表格及代码样式；复制操作按需提供。
- 工作进展：显示真实阶段、已完成事项与下一步，记录默认折叠；不重复插入没有新内容的状态消息。
- 空闲：移除每轮常驻的“可以继续交流”状态行，输入提示即可承担邀请继续的作用。
- 正在处理：在本轮回复附近显示“正在理解／整理方案”等准确状态，用户可继续补充；暂停任务入口与发送补充入口分别保留。
- 已暂停：显示输入只会先保存、明确恢复后继续处理；暂停收尾中与已经暂停分开说明。
- 缺少条件：说明缺什么、仍能做什么及下一步。例如“可以讨论和生成方案，代码运行与测试环境尚未连接”。
- 用户阅读历史时保持位置并提供“有新回复／回到最新”；在底部时跟随新增内容并保留输入焦点。

状态颜色：中性／低饱和色用于处理中，绿色用于成功，琥珀色用于等待与缺条件，红色用于失败；文字同时说明含义。

## 5. 输入区

正文与工具栏分层，工具栏只保留附件、工作模式、发送。正文自动增高，最大约240px；桌面窗口高度不足时进一步限制正文高度，长输入在内部滚动，工具栏保持可用。

模式显示完整“计划模式／执行模式”。简短说明解释权限：计划先分析和给方案，执行按目标授权推进。缺执行资源时显示实际可用范围，不静默改变用户选择的模式。

发送按钮：空输入为禁用，有正文或附件时明确可用，接收后给出持久保存状态；处理中的用户仍可补充。发送失败、未知回执、未保存文件等恢复区域保留在就近位置。

正文在输入法组字期间不发送；Enter换行、Ctrl/⌘+Enter发送的现有行为保留。快捷键提示按焦点显示。

## 6. 方案确认与成果

待确认方案在对话中以单张卡片展示：名称和版本、本期范围、关键约定／不包含项、必要检查与确认动作。

- 执行条件具备时，主按钮可为“确认并开始”。
- 仅保存确认时，主按钮必须为“确认方案”，明确确认后仍需等待的条件。
- 次操作为“调整方案”和“查看完整方案”，不与主操作争夺视觉重点。
- 确认绑定用户实际看到的Run、需求／计划版本、资源版本与reviewHash。方案变更后旧卡只供核对，不能确认新版。
- 用户仍可用自然语言确认或提出修改；按钮与文本入口保留一致的授权语义。

成果卡片使用准确候选与已接受版本事实。主操作按情况为“查看效果”，辅助操作为检查结果、变更文件和交付材料。候选、已接受、已发布分别标识，缺实际入口时说明条件。

## 7. 导航、顶部和执行详情

侧栏支持展开／收起，按今天、近7天、更早组织实际会话；名称语义化，选中项明确。搜索的覆盖范围须与实际能力一致，全量搜索如需后端扩展另列。

顶部只保留短任务标题、当前必要状态、详情入口。省略重复面包屑；长标题截断并提供完整内容。桌面顶部建议56px。

右侧保持默认收起，建议宽320～360px。并排后正文不足640px时改为抽屉。内容分为本轮目标、当前工作／资料、变更与验证、能力／阻塞信息。完整方案和工作记录尽量在当前工作区查看，明确的专用预览／下载才跳转。

在桌面窗口内打开或关闭详情后，返回原对话位置，草稿、附件和键盘焦点保持。

## 8. 视觉基准

保留石墨黑基调。建议主背景#19191C、侧栏#121214、输入与轻表面#242428、正文#EFEFF2、辅助文字#ACACB6、边线#34343B。主按钮使用灰白，语义色仅表达状态。

字号：品牌18～20px、欢迎标题28～32px、正文16px、次级信息12～13px。间距以8px为基本节奏，内容块16／24／32px。输入与方案卡圆角12～14px，普通控件6～8px，边线1px。

正文对比度目标至少4.5:1，焦点轮廓可见；交互不能只靠颜色和悬停。主要操作支持鼠标和键盘，按钮层级及焦点顺序明确。

## 9. 分阶段实施

**第一阶段：桌面阅读和操作空间。** 统一宽度、字号和间距，精简首页卡片，调整消息样式、输入自适应、桌面顶部、侧栏折叠和必要能力提示。优先复用现有接口与真实状态，不改变授权及执行条件。

**第二阶段：对话中的决定与结果。** 完成准确方案卡、按钮直接确认、任务标题、语义化状态和真实详情／成果呈现。涉及确认命令日记、持久会话消息、改名或搜索接口的内容单独列契约与后端工作，不把它们记作纯样式调整。

两阶段均保留原始请求核实、事务失败、跨页冲突、历史只读与权限边界；不以视觉改造开放执行权限。

## 10. 验收

- 1600／1440／1280／1024px桌面窗口下没有页面横向溢出；主要操作始终可达。
- 空输入不长期占用过多屏幕；正文、输入和方案卡同宽对齐。
- 长回复、代码、列表、附件、错误及恢复区域保持可读。
- 已确认方案、等待确认、处理中、暂停中、已暂停、完成和缺条件均可区分。
- 缺执行资源时仍可讨论和审阅，不能出现已经开始运行代码的误导文案。
- 确认动作不再需要重复点击发送；方案版本改变后旧确认被正确拒绝。
- 切换详情、任务、刷新、重新连接时，已有草稿和原请求继续保留。
- 保存桌面首页、对话、计划确认与缺条件状态的实际截图；设计示意和真实执行证据分开。
