# DevMesh 对话式 Agent 工作流详细修改计划

日期：2026-11-18

状态：用户于2026-11-18授权实施，实施与验收进行中

范围：面向 Web 应用研发的主助手、持续对话、任务编排与工作台交互。

本文为本次授权实施依据，不代表全部能力已经完成。具体进展和证据记录在 implement-conversation-agent-workflow 变更；正式工作包和阶段门槛按实际验证分别维护。

## 1. 目标体验与实施原则

用户在同一条对话中交办目标、回答问题、补充要求、查看进展、调整方向和验收结果。主助手负责理解上下文、选择下一步、组织专业 Agent、调用现有工具、检查结果及交付。

产品、架构、开发、测试四类 Agent 保留专业分工；主助手作为统一对话与调度入口，复杂研发按需组织多角色，简单咨询直接回答。A2A、MCP、代码工作空间、DAG、实际验证与交付能力复用现有实现。

用户看到的是有内容的回复、必要的进展和可查看的成果。需求版本、工作依赖、Agent 交接、原始执行记录通过详情查看。

新会话建议默认执行模式；输入框允许选择计划模式。用户的明确自然语言约束优先，例如“先给我方案，别改代码”。旧任务保留原授权语义，不能因界面升级自动扩大执行权限。

## 2. 已核实的现状与缺口

| 现状 | 影响 | 拟修改 |
| --- | --- | --- |
| 当前 workspace 消息投影主要是用户输入，助手内容以理解／计划和临时模型片段呈现 | 提交后直接进入管理视图，缺少连续、可恢复的助手回复 | 新增正式的对话消息与助手轮次记录 |
| 需求理解输出要求至少一条结构化需求，输入进入准备处理链 | 咨询、打招呼、补充和开发要求缺少合适分流 | 增加主助手的意图与动作协议，开发分支复用原严格需求契约 |
| PRD §3.2 要求首次实现前人工确认具体计划 | 默认执行模式无法仅靠前端去掉按钮实现 | 增加范围明确的执行授权，修订调度准入；计划模式保留具体计划确认 |
| 对话选择与项目／Run 紧耦合 | 持续补充、执行中纠偏、完成后继续交流容易变成“下一目标”表单 | 对话作为稳定入口，实际执行通过关联记录绑定 Run |
| 主区直接挂载计划总览和下一目标入口 | 用户需要理解内部状态并主动找结果 | 主区改为连续消息，完整规划及工作记录进入可展开详情 |
| 实时进展与工作区刷新分开，用户需要查看更新 | 已完成的分析或计划不自然接续到对话中 | 自动更新只读对话投影，保留正在编辑的内容与审阅依据 |

上述结论依据当前 contracts/input.ts、contracts/preparation.ts、agent-runtime/preparation.ts、storage-sqlite 的输入／理解／准备处理及工作台组件。

## 3. 用户交互规则

### 3.1 两种模式

| 模式 | 可开展的工作 | 何时等待用户 |
| --- | --- | --- |
| 执行 | 根据明确目标调查、规划、修改、测试、修复并交付 | 缺关键资料、范围有重大变化、超出本次授权或需要用户裁决 |
| 计划 | 阅读、分析、评估、生成方案与计划草案 | 用户明确确认当前有效方案后才开始实现 |

模式属于任务执行约定。普通问答在任何模式下均可直接回应；“咨询”不等于“同意采用回答中的建议”。

“修改吧”“按这个做”只能承接已展示、仍有效且指向清楚的方案。存在多个方案、版本过期或范围不明时，先确认对应对象。切换模式不得追溯性授权已经提出但尚未获准的额外操作。

### 3.2 处理不同输入

| 输入类型 | 例子 | 系统行为 |
| --- | --- | --- |
| 咨询 | “这个系统的权限怎么设计？” | 结合上下文回答；不因回答而自动更新实施范围 |
| 开发目标 | “帮我做一个内部工单系统” | 确定目标与条件，必要时澄清，按所选模式推进 |
| 补充／调整 | “先不做登录，再增加状态筛选” | 关联当前目标，评估影响，安排后续工作或明确范围变更 |
| 回答澄清 | “只给内部员工使用” | 关联具体问题与版本，保存用户明确表达的答案；歧义继续确认 |
| 过程询问 | “现在做到哪一步？” | 从真实任务、工具和验证事实生成进度摘要 |
| 控制 | “暂停一下”“继续刚才的工作” | 识别明确对象后进入既有暂停／恢复协议 |
| 新目标 | “这个结束后，另外做一个预约系统” | 区分当前任务补充与独立新任务；目标不明时询问 |

“如果测试失败就停止”是约束，“暂停当前任务”是控制。不能只用关键词触发暂停、取消或执行确认。

### 3.3 回复内容

首轮回复根据实际输入说明理解和下一步，避免每次使用冗长固定模板。可以直接开始调查；有影响结果的缺口时才询问。中间进展解释完成了什么、正在做什么和需要处理的问题。最终回复提供成果入口、完成范围、实际检查结果和未完成项。

临时模型片段属于生成中状态，完成并保存后才成为正式回复。原始结构化输出不作为主区助手正文。第一步先实现完整回复的可靠保存与恢复，再接面向用户正文的流式展示。

## 4. 主助手执行循环

1. 持久接收用户消息、附件引用、任务模式及客户端请求身份。
2. 按当前身份与权限读取对话、项目、执行、最新指令、已有成果及必要资料。
3. 在一次主助手决策中生成用户回复和有类型的后续动作；不为每条消息固定串联“分类模型、需求模型、架构模型”。
4. 服务端核实动作的权限、模式、范围、输入依据与预算，再执行工具或委派专业 Agent。
5. 保存真实工具结果、交接回执、方案或交付结果；向对话投影可读的进展。
6. 观察结果后决定继续、修复、等待回答或交付，直到达到完成条件或进入明确等待状态。

模型可建议回复、读取资料、澄清、需求理解、规划、委派、验证与结束；具体领域命令由服务端适配现有接口并校验。模型文本中的“完成”不能代替实际完成检查。

同一对话的主控决策串行处理，专业工作按已有依赖关系并行。每轮决策绑定输入序号、当前目标版本和执行依据；新指令到达后，旧决策不能覆盖最新目标。执行步骤、重试、修复和 Token 使用沿用有界配置，耗尽时说明已完成部分和下一步条件。

### 4.1 对话状态

| 状态 | 用户看到的反馈 | 可继续的条件 |
| --- | --- | --- |
| 已接收／排队 | 消息已收到，等待开始 | 调度获得可执行条件 |
| 理解／工作中 | 简洁阶段说明，必要时附折叠工具摘要 | 新事实到达后自动推进 |
| 等待回答 | 对话中的必要问题 | 用户提交有效回答 |
| 等待确认 | 具体方案摘要及确认／调整入口 | 当前方案取得适用授权 |
| 暂停收尾／已暂停 | 明确区分正在收尾和已经暂停 | 收尾完成，之后由用户明确恢复 |
| 结果待核实 | 原动作和输入继续保留 | 核实原动作结果，不盲目重发 |
| 受阻 | 具体原因与可处理入口 | 对应条件解除；需要执行授权时明确继续 |
| 已完成 | 成果链接、验证结果、剩余事项 | 后续补充进入同一对话，按事实关联新的执行 |

后台领域状态继续保留原定义；本表是对话展示与交互投影，不能用展示状态覆盖真实控制状态。

## 5. 会话、消息、执行与授权的数据边界

| 对象 | 责任与拟记录内容 |
| --- | --- |
| Project | 应用代码、成员、接受版本及长期资产 |
| Conversation | 用户连续对话入口；所属主体／权限范围、可选项目绑定、模式、目标版本和关联执行 |
| Message | 用户或助手正文、附件、顺序、关联用户输入、关联轮次／执行、保存时间 |
| AssistantTurn | 本轮处理的输入边界、上下文版本、模型配置快照、状态及输出消息 |
| Action | 有类型的动作、准确请求身份、输入依据、实际结果及核实状态；引用现有工具／A2A／领域操作 |
| ExecutionAuthorization | 谁在何时授权了哪个目标、范围、模式和约束；授权更新、收回与适用版本 |
| Run | 一次实际研发执行及其计划、工作、代码、验证和交付事实，继续采用现有领域实体 |

会话可在尚未开发时存在；进入实际研发时再绑定或创建项目及 Run。与已有项目关联的会话可直接使用其当前上下文。连续输入不自动新建独立 Run，也不直接改写旧 Run 的冻结依据。旧 Run 仍按原只读／历史规则查看。

新增数据采用向前迁移。旧用户消息、项目、Run 和原请求历史保留；旧记录没有助手回复时如实展示，不能补写虚构的历史回复。临时片段与最终保存消息明确区分。最终回复及动作应用有去重约束，服务重启或丢回执后不重复应用。

## 6. 执行授权与原计划确认的衔接

这是本次需要同步修改的产品与领域规则。

- 计划模式：实际实现继续需要用户对当前方案／计划明确确认；确认绑定准确版本、范围和依据。
- 执行模式：用户发送目标时形成持久、可审计且范围明确的任务执行授权。服务端检查当前计划是否满足授权及原质量准入后，才允许调度。
- 自动执行授权与“用户亲自确认了某一份具体计划”是不同事实，分别记录，不能由后台自动点击原按钮或伪造人工确认回执。
- 未解决的必要问题、无效计划、缺少实际执行资源、角色权限不符等准入条件继续生效。执行模式不意味着跳过这些条件。
- 执行中范围变化需要更新目标与授权，已发出的工具／Agent 操作按原协议收尾或核实；不能把新目标套用到旧请求上。
- 自动实施与最终交付接受分开。是否接受某个版本继续是明确动作，不能因测试通过自动代替用户接受。

## 7. 前后端接口与页面改动

### 7.1 接口草案

拟新增会话创建／列表、准确会话消息分页、消息提交和只读能力状态接口。最终路径与字段在 CW-01／02 固定，下面是责任划分而非已发布 API。

| 责任 | 关键约束 |
| --- | --- |
| 创建／读取会话 | 主体、项目成员、模式、可选项目绑定、读取分页有界 |
| 提交消息 | 客户端消息 ID 与 Idempotency-Key；持久接收后返回消息及处理身份；不在 HTTP 请求中等待整次研发完成 |
| 读取消息与动作摘要 | 依照会话序号分页；刷新后读取持久内容；不能把缺失片段当最终结果 |
| 执行授权与范围更新 | 有版本条件的显式动作；权限、目标、范围可核实 |
| 运行控制 | 适配已有 Run 暂停／恢复／取消接口，保持唯一领域控制事实 |
| 实时事件 | 扩展现有同源事件能力，按准确会话／执行授权、补取及去重；保留旧 Run 订阅兼容 |
| 能力状态 | 返回服务实际是否接入模型与所需执行能力、配置是否待生效及可处理原因；不返回凭据 |

普通消息的追加不能因为一条后台进展更新就产生无意义的版本冲突；确认、控制、授权和范围变更则必须检查准确业务依据。

### 7.2 页面

左侧保留项目导航，并承载项目中的任务会话记录。选中会话后，中间一直显示同一条对话，输入框保持底部。

输入框保留正文、附件、发送及一个轻量“执行／计划”切换入口。运行中允许补充指令，并提供明确暂停／停止入口；“消息已收到”与“已应用到后续执行”分别反馈。

主区按时间顺序显示用户消息、助手回应、阶段进展、必要问题、确认卡片和交付卡片。工具、文件变更、Agent 分工及错误详情默认折叠。完整计划、DAG、来源、日志放在现有可收起执行区。

根视图取消无意义的“返回上一级／任务总览”。“项目下一目标”移出默认输入流程；完成后的后续目标用同一对话承接，必要时明确创建新的执行。已有待核实原请求保留独立恢复入口。

自动更新只替换只读消息和进展投影，不清空输入、附件、选择或正在填写的澄清表单。新方案改变正在审阅的依据时明确提示，不能将旧同意套用到新版。

## 8. 实施步骤、依赖及交付物

CW 编号只是本草案内部步骤，不新增或替代 project/tasks.json 的正式工作包。

| 步骤 | 内容与交付物 | 依赖 | 验收条件 |
| --- | --- | --- | --- |
| CW-01 规则与契约设计 | 固定两种模式、意图／动作类型、会话边界、授权语义及页面状态；建立 OpenSpec 变更并同步受影响设计 | 无 | 输入例子有唯一预期；执行授权与具体计划确认区分清楚 |
| CW-02 存储与迁移 | 会话、双方消息、轮次、动作关联、授权、版本与去重；旧记录兼容 | CW-01 | 重启／丢回执不重复应用；旧项目与原记录可读 |
| CW-03 会话 API 与上下文 | 有界消息读写、主体隔离、附件引用、按需读取上下文、能力状态 | CW-02 | 两个会话不串内容；重复提交得到同一原结果；无权不能读写 |
| CW-04 主助手 Runtime | 意图与自然回复、动作校验、工具／Agent 路由、观察与继续、完成条件、预算 | CW-03 | 真实运行咨询／澄清／研发分支；失败和未知结果各有适当后续动作 |
| CW-05 专业流程与授权调度 | 复用四角色与 DAG；按模式实施；范围变更、必要问题和质量条件检查 | CW-04 | 计划模式无实现操作；执行模式在授权内完成真实实现与验证；审计没有伪造人工确认 |
| CW-06 执行中补充与控制 | 输入序号、过期决策作废、指令接收与应用、暂停收尾／恢复、任务完成后的延续 | CW-04、05 | 新指令不被旧响应覆盖；暂停后不擅自恢复；新旧执行依据清楚 |
| CW-07 对话 UI 与事件投影 | 连续消息、模式、阶段进展、折叠工具、确认／交付卡片；右侧按需详情及宽窄屏 | CW-03；CW-04／05 接口稳定 | 提交后得到自然回复；不再直接进入管理总览；输入和原恢复记录保留 |
| CW-08 可用性与交付入口 | 真实模型／工具／工作空间状态；预览、文件、版本、验证结果关联准确执行 | CW-05、07 | 配置已保存与运行时可用分开；交付链接来自真实记录且指向准确版本 |
| CW-09 联调、迁移复核与发布准备 | 功能矩阵、故障恢复、实际模型与真实执行验证、证据、文档／台账同步 | CW-01～08 | 下节场景取得真实结果；检查与环境缺项分别记录 |

建议形成三个可验收里程碑：

1. CW-01～04、CW-07 的基础部分：连续对话、真实自然语言回复、咨询分流、持久恢复及准确阻塞反馈。
2. CW-05、CW-07 的执行部分及 CW-08：计划／执行模式、一轮研发的实际实现—验证—交付闭环。
3. CW-06、CW-09：执行中纠偏、暂停恢复、跨执行延续、完整故障与升级验证。

三者均属于最终目标。里程碑一只能证明对话链路，不能被当成持续执行工作台已完成。

## 10. 验收场景

| 场景 | 必须观察到的结果 |
| --- | --- |
| 首次输入“你好”／单纯咨询 | 得到适当回复，能继续交流；不虚构开发需求或启动实现 |
| 输入明确研发目标 | 回复理解与下一步；执行模式实际推进，计划模式先给方案 |
| “先给计划，不改代码” | 分析与方案可读；没有实现类副作用 |
| “按这个修改” | 关联准确有效方案；对象不明或方案变化时先确认 |
| 回答问题／增加明确要求 | 前文可承接，必要答案可追溯，原附件保留 |
| 执行中增加或删减范围 | 明确接收与应用；旧决策不覆盖新要求；已发动作有明确收尾 |
| 暂停、恢复、取消 | 控制对象准确；暂停收尾与物理完成区分；回答问题不等于恢复 |
| 模型缺失／已保存待生效／工具不可用 | 显示实际原因；输入保留；不展示虚构进度或成功 |
| 请求丢回执、重复点击、刷新 | 核实同一原请求，消息／回复／动作不重复生效 |
| 断线、乱序、迟到响应、身份变化 | 按序恢复、旧上下文不污染当前对话；撤权及时清除投影 |
| 必要问题未答／计划不合格／授权范围不符 | 实现被正确阻止，说明具体需要处理的条件 |
| 原模型 JSON／片段中断 | 主区没有原始结构化噪声；未完成内容与保存结果区分 |
| 完成与继续迭代 | 交付实际预览／文件／版本和验证结果；后续对话可接续，旧成果身份不被混用 |
| 历史项目升级与 390px 窄屏 | 旧记录真实可读，原草稿与恢复仍可用；输入及主要操作可达 |

按改动执行契约／存储迁移、Runtime／调度／控制、HTTP／事件、实际浏览器及构建／类型／Lint 检查。先用受控模型与真实存储验证确定性分支，再使用可用的真实模型、工具与执行环境完成端到端任务。夹具结果、真实模型效果、Linux Runner／隔离／物理停止及完整产品验收分别记录。

## 11. 上线、兼容与完成定义

先在独立测试数据上完成迁移与真实任务验证，再对新建会话启用新流程。旧入口和旧任务保留兼容，切换时保留原模式、原请求和历史依据。

新流程采用可关闭的准入开关。关闭新任务准入后，对已发动作先核实与收尾；数据库不通过删除历史或回退旧迁移来恢复。升级与回退前保留可恢复的数据备份。

批准实施后同步 PRD、D3 及受影响技术专题、生成主文、实施文档、验收场景、OpenSpec proposal／design／tasks／增量 specs、台账基线和实际证据。实施结束提供可运行服务、真实页面截图和端到端记录。

完成的判定是：用户交办目标后，系统能理解并持续执行；用户能在同一对话纠偏和控制；过程状态真实、已保存结果可恢复、最终成果可验收。仅调整页面文案、出现回复或后台生成一份计划，都不能单独视为完成。
