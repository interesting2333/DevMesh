# DevMesh 执行详情精简方案

日期：2026-11-20。状态：三页签实施已按用户要求回滚；当前保留为方案。

关联父工作包：P1-08；后续实施沿用 `refine-desktop-conversation-ui`。当前应用恢复五页签与顶部精简版本；本方案不代表当前已生效能力。

## 1. 核心建议

将五个页签收敛为 **进展、成果、记录**。协作分工并入进展，预览并入成果。

用户首先看到当前情况和下一步，具体版本、证据、运行管理按需展开。对话继续负责需求沟通、补充和计划确认，执行详情负责查进度、看结果及追溯。

| 当前入口 | 调整后位置 | 用户看到的含义 |
| --- | --- | --- |
| 任务／概览 | 进展 | 现在做到哪了，需要我做什么 |
| 协作 | 进展中的“工作分工” | 谁负责哪部分，是否已经开始 |
| 成果 | 成果 | 目前做出了什么，检查结果怎样 |
| 预览 | 成果中的“查看效果” | 打开所选版本的应用体验 |
| 记录 | 记录 | 重要决定、失败和版本变化 |

## 2. 进展：当前情况 → 下一步 → 工作分工

默认展示三块，按顺序排列：

1. **当前情况**：用一句话说明阶段或阻塞，例如“方案已准备好，等待你确认”。不重复任务名和模式解释。
2. **下一步**：有待办时提供一个首要操作，例如“查看方案”“补充说明”“查看问题”；需要确认的方案仍定位主对话中的原方案卡。没有待办时显示真实当前工作，不推测下一项已经开始。
3. **工作分工**：按工作展示角色、工作目标和状态。区分“计划分工”和“实际执行”，没有 Agent 绑定时只称角色，不写具体 Agent 在线。

需求和完整方案放在“查看需求与方案”折叠区，配置、工作ID和技术依据放在“高级信息”。交接与工具调用当前缺少页面投影，不在首屏放空白占位区；已有技术记录入口保留在高级信息中。

普通状态下，页签上方不再另设摘要。需要注意的信息与下一步在进展内保持同一来源；用户正在其他页签时，只给“进展”一个真实待办标记，不重复完整提示卡，也不自动切走。

## 3. 成果：版本摘要 → 查看效果 → 检查与交付

默认展示一份明确标识的版本，顶部依次显示：

- 版本名称和状态：例如“待审查版本 1”“已接受版本 1”。
- 简短说明：说明已完成的检查及仍待核实的事项。
- 一个主要操作及适用的次操作：优先查看实际效果，之后查看检查、接受和交付材料。

### 版本选择

用户已选择的版本优先恢复。首次进入时，仅在服务端能确定本轮最新版本时默认选中；不能确定就明确要求选择。历史版本放入“其他版本”折叠区。

项目已经接受的版本单独标为“项目当前使用版本”，注明是否来自其他执行；不得混称本轮生成的版本。新版本出现只提示，不自动替换正在查看的版本。

### 预览与交付操作

| 实际情况 | 成果页的主要呈现 |
| --- | --- |
| 尚无产出 | “当前还没有生成可查看的版本”，并提供回到进展的入口 |
| 已有版本，尚未启动预览 | “预览尚未启动”，提供“准备预览”或运行条件入口 |
| 预览访问可用 | “查看效果”为主操作，打开准确版本的应用 |
| 运行条件缺失／状态未知 | 一句话说明原因，提供查看条件或核实状态；不显示无效的打开按钮 |
| 需要审查／接受 | “查看检查结果”“确认接受此版本”进入原准确版本的审查／接受流程 |
| 已形成交付材料 | 展示“下载交付材料”，指向已接受版本对应的材料 |

数据准备、启动、停止等操作放在“预览管理”次级入口，继续使用原专用管理页和确认流程。首屏不展示完整运行参数和实例历史。

“查看效果”承接用户了解成果的目的，预览状态与交付状态分别标识：体验应用不会接受版本，系统检查通过不会自动代表人工验收完成。侧栏以摘要和入口为主，应用体验使用新窗口，避免在窄栏嵌入完整应用。

## 4. 记录：默认关键节点，详细日志按需查看

优先显示四类事项：重要确认、工作失败与恢复、版本形成、接受与交付。

默认不逐条铺开“输入已保存”“工作状态已更新”等高频通知。完整的当前可读事件放在“详细执行日志”中，明确最近最多50条的实际范围；失败和未知结果不能因精简被隐藏。

每条关键记录说清楚“何时、发生了什么、结果怎样”，可定位原工作、版本或证据。未知类型保留原类型到详细日志，并提示有未分类记录，不推断为成功。

如果现有事件只提供类型而没有结果明细，则仅显示能够核实的事件事实和技术入口；补充完整原因与关联详情另列后端投影工作。

## 5. 统一文案与显示层级

| 当前表达 | 建议表达／位置 |
| --- | --- |
| 已冻结候选、候选版本 | 待审查版本；固定版本的技术含义放到高级信息 |
| 当前依据 | 对应当前需求和方案 |
| 旧依据，只读核对 | 对应之前的需求和方案 |
| 尚未派发 | 尚未开始；展开时再说明等待原因 |
| 自动检查已通过 | 系统检查已通过，实际功能和审查结果仍需查看 |
| 配置代际、部署修订、代码哈希、Run ID | 仅在高级信息或详细日志中展示 |

首屏只放与用户下一步有关的信息；摘要、来源和技术字段形成逐层展开关系。不把读取失败写成“暂无成果”，不把未知结果写成“尚未开始”，不隐藏权限或环境造成的真实阻塞。

## 6. 典型使用路径

用户描述采购系统需求 → 主对话讨论并生成方案 → 进展显示“等待确认方案” → 回主对话确认 → 进展显示实际开发／验证状态 → 成果出现待审查版本 → 查看效果与检查结果 → 单独确认接受 → 下载材料。

尚未连接代码执行环境时，进展明确说明仍能讨论和规划，成果不显示已经开始开发或生成应用。记录用于核对已经发生的重要事实。

## 7. 实施顺序和验收

先做页签合并、内容重排和文案调整，复用现有状态和专用页面；再补充当前接口不能可靠提供的阻塞原因、关键事件详情和关联定位。后台能力缺项不影响先完成有据可查的界面精简。

验收要求：

1. 默认仅有进展、成果、记录三个页签，原五项内容均有明确归属。
2. 进展首屏能找到当前情况和下一步；查看分工不必进入独立协作页。
3. 同一版本在成果内完成查看效果、检查与交付导航，不必跨成果／预览页签来回找入口。
4. 普通首屏不出现候选冻结、配置代际、哈希等内部术语，技术依据仍可展开查看。
5. 切换、刷新和返回保留版本、草稿、附件及原请求；普通查看不自动提交确认或控制命令。
6. 旧页签偏好迁移：任务→进展，协作→进展／工作分工，成果→成果，预览→成果／查看效果，记录→记录；原所选版本和专用页返回上下文保持。
7. 空态、读取失败、未启用、历史只读、未知状态和跨执行项目版本分别验证，不为减少信息而改变事实。

本方案建议先完成这版精简，再根据真实使用反馈决定是否需要独立的协作大视图或内嵌应用预览。
