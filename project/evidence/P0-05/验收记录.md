## 关键验证与技术复核

- 清单同 revision 同内容复用代际，端点版本不可改；同 revision 异体、旧清单自动回切、CAS 变化和不完整健康集合拒绝，失败事务不留下部分角色新代际。
- 实际 HTTP 监听后再请求本机 Card，准备中 healthz 可读而 readyz 503。独立端点健康分别记录，缺凭据入口 401；过期／NEEDS_REVIEW／DRAINING 阻止新执行。迟到探测只归档，相同清单不清除维护排空。
- 官方 ClientFactory 经真实 HTTP 发起 5 次并发同请求，仅一个 Task、Inbox 和 AcceptedWork；同 operation 异体冲突。GetTask／ListTasks／SSE／取消经 SDK 编解码，主体隔离成立；未知私有 RPC 方法被标准层拒绝。
- PENDING 取消可核实无消费者副作用；ACTIVE 取消仅记录意图，核实停止前保持 working。完成依赖当前持久 claim token 与已知工具／Runner 状态，不把连接中断视为停止。
- SQLite trigger 在受理事务中注入失败，三种记录全部回滚；投影读取失败关闭准入，恢复后从已提交 DB 代际重建。
- 两个真实 SIGKILL 切点：受理提交后重启返回原 Task；消费领取后重启 ACTIVE→RECONCILE，消费者不能再领取。原 Task 和唯一收件记录保留。

复核覆盖正式 SQL／外键、不可变端点／代际、健康序号与有效期、配置→DB→投影、准入 DB 复查、服务身份、请求哈希、SSE 断线与资源释放、SDK 类型／协议边界和原始证据。SDK Card 中间件直接序列化对象，已用官方 AgentCard.toJSON 转换 oneof，避免泄漏 `$case` 内部结构；真实官方客户端已验证。未发现阻止 P0-05 基础完成的问题。
